# Test restore before launch

This is a PostgreSQL logical database archive encrypted by age. It includes captured database schemas/data, including Auth/private CRM metadata, but **does not include Storage object bytes**, company secrets/environment settings, SMTP/Meta configuration, role passwords or a point-in-time history. Database success is not full disaster-recovery success. Supabase also excludes Storage objects from its database backups. [Supabase backup scope](https://supabase.com/docs/guides/platform/backups)

Use a **separate test project**, never the live CRM. Keep outbound mail, Meta and jobs disabled in the test environment so restored records cannot contact real customers or reassign them. Protect dump files as customer/account data. A database snapshot contains encrypted Meta tokens and Auth data; securely retained matching encryption keys and project configuration are needed, and copied access tokens are not assumed valid across projects.

1. Keep the age identity/decryption key offline with the owner. Copy one encrypted archive off the VPS. Compare its SHA-256 with `public.backups.sha256` using trusted database administration; inspect the recorded bytes/status/date. Do not store the identity on the backup server.
2. On a trusted temporary machine, install age and PostgreSQL client tools matching or newer than the source database. Set umask 077. Decrypt into a private temporary directory using `age --decrypt --identity /secure/owner-key.txt --output /secure/restore-test.dump /secure/hd-crm-ARCHIVE.dump.age`. This is an example path; choose your own private paths. Never use production connection credentials for a restore.
3. Inspect with `pg_restore --list /secure/restore-test.dump`. Keep the original archive immutable. A raw full `pg_dump` also captures Supabase-managed schemas. **Do not blindly restore those schema definitions over a newly provisioned Supabase project.** Use the provider's [project migration/restore procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) and a qualified operator to select/reconcile Auth/Storage data, required extensions and managed roles. PostgreSQL tools document selective restore using an edited list file. [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html)
4. For public/crm_private application schema testing, use `pg_restore --schema=public --schema=crm_private --no-owner --no-acl --exit-on-error --dbname=TEST_CONNECTION /secure/restore-test.dump` **only after preparing dependencies in the separate test project**. Foreign keys reference Auth users: coordinate restored Auth identities through the supported migration procedure before app data, or the restore will fail. The sample command is not an unattended full Supabase-project restore. Use connection environment/PGPASSFILE on the operator's machine to avoid credentials in argv/history.
5. Explicitly reapply the CRM's intended grants using reviewed migration SQL. `--no-acl` archives do not preserve permission grants. Confirm direct anon/authenticated reads/RPCs/private buckets are denied. Test the recipient-confirmation and active-profile gates; do not auto-confirm copied accounts.
6. Restore Storage objects with a separate object backup/export. Reconcile bucket/object identities and prove photo display and an authorized policy download. Missing object content must be reported; restoring only database references cannot recreate files.
7. Check CRM row counts, foreign keys, private phone ownership, audit history, jobs/migration status, Accounts PIN reset, optional-agent MFA and new password login against the isolated test configuration. Keep automatic jobs disabled until the data is reviewed. Retain a count-only restore report and date outside this database.
8. Remove decrypted temporary data securely according to the device/storage policy. Keep encrypted copies and the owner's offline key independently. Schedule restore rehearsals and off-VPS copies; storing everything on one VPS cannot survive VPS loss.

No real dump or hosted restore was performed by Codex. The backup pipeline is locally tested for encryption/command errors, safe metadata, private files and retention. The real provider connection, Storage export and separate-project restore remain mandatory acceptance work once infrastructure exists.
